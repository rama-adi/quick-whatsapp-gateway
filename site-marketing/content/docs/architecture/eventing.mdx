The eventing subsystem has two halves that share one envelope:

1. **Normalization** (`backend/internal/wa/events`) — translate raw whatsmeow events into the
   versioned domain event catalog (§11), classify chats, and apply source-level ignore
   rules. Documented here.
2. **Transport** (`backend/internal/stream`, `backend/internal/webhooks`) — the realtime WebSocket and the
   webhook dispatcher that carry the envelope. Documented in their own specs and the
   transport section below (owned by another subsystem).

The shared envelope is `domain.Event` (schema `v1`): `&#123;schema, id (evt_&lt;ulid>), event,
session, organization, timestamp (epoch-ms), payload&#125;` — see `backend/internal/domain/event.go`.
The envelope carries the **owning organization** (`organization`, a better-auth org id)
so every transport can scope delivery by org. The catalog includes interactive selections as `message.interactive_reply`.

**Auth (per §4).** Realtime ticket minting authenticates with the API's two-acceptor
middleware — a JWKS-verified better-auth **JWT** (human) or a better-auth **api-key**
(machine). There is no event-specific auth path; the resolved org scopes what a caller
sees. Outbound webhooks use their configured HMAC signing secret.

## Normalization (`backend/internal/wa/events`)

### Scope

Pure, dependency-light translation. The package imports only the Go stdlib, whatsmeow
(`types`, `types/events`, `go.mau.fi/whatsmeow/proto/waE2E`, `go.mau.fi/whatsmeow/proto/waCommon`) and `backend/internal/domain`. It holds
no IO and no live client, so it is trivially unit-testable and parallel-safe. Collaborators
(config) are consumer-defined here (`IgnoreConfig`).

### Key entry point

```go
func Normalize(evt any, sessionID, organizationID string) (domain.Event, PersistResult, bool)
```

- Switches over the handled whatsmeow event types and returns:
  - a `domain.Event` envelope whose `Payload` is a **wire-safe, camelCase struct** — never
    a raw protobuf;
  - a `PersistResult`, the structured, protobuf-free handoff the inbound pipeline consumes
    (capture → persist → fan-out, §9), so downstream stages never re-parse the raw event;
  - `ok=false` for events the catalog does not represent (the caller drops them).

### Message sub-type detection

`normalizeMessage` reads `e.Message` (the lib already unwraps
Ephemeral/ViewOnce/DeviceSent/Edited). Detection order (control messages first):

1. Native-flow, button, or list selection → interactive reply.
2. `GetReactionMessage()` → reaction (emoji + target id from the `MessageKey`).
3. `GetProtocolMessage()` type `REVOKE` → revoke (target id).
4. `e.IsEdit` or `ProtocolMessage` type `MESSAGE_EDIT` → edit (new body from
   `GetEditedMessage()`, target id from the key). Note: the real constant is
   `ProtocolMessage_MESSAGE_EDIT` (value 14), not the `EDIT` the recon cheat-sheet implied.
5. `GetPollUpdateMessage()` → poll vote (target poll id; the vote payload stays encrypted
   here — decryption + option-text resolution happen in the composition-layer normalizer,
   which holds the whatsmeow client and the stored poll options, see below).
6. `GetPollCreationMessage()` **or** `GetPollCreationMessageV2()`/`V3()` → poll
   (name/options/selectableCount/endTime/hideVotes). Current WhatsApp clients send the V3
   field; checking only the original (pre-V2) field was why modern polls were misclassified as a
   content-less "system" message and dropped. (V4+ wrap the poll in a `FutureProofMessage`
   and are not handled.)
7. `GetLocationMessage()` → location (lat/long/name/address).
8. `GetContactMessage()` → contact (displayName + vCard verbatim).
9. Any media message (image/video/audio/document/sticker) → media metadata plus a private attachment descriptor for API-side capture.
10. `Conversation` or `ExtendedTextMessage` → text.
11. otherwise → `system` / `SubtypeUnknown` (still emitted as a `message`).

### Extracted fields (`NormalizedMessage`)

Maps ~1:1 onto the `messages` table plus identity/contacts capture inputs:
chat JID + `ChatClass`, sender phone JID and sender LID (classified by server from either `Sender` or
`SenderAlt`, with device suffixes removed), `FromMe`, push name, epoch-ms timestamp, body/caption, quoted stanza id,
mentioned JIDs (stored internally as a list, emitted on message events as a
JID-keyed map containing `pushName` and per-group member `tag` when known), media
flag + `MediaMeta` (mimetype/size/filename), reaction/edit/revoke target id, and
structured `Location`/`Contact`/`Poll` bodies.

**Quoted-message context (replies).** A reply's `ContextInfo` carries the quoted
message inline, so message events expose the quote without a REST round-trip:

- `quotedSenderJid` / `quotedSenderLid` — the quoted message's author, from
  `ContextInfo.Participant` (canonicalized to non-AD; routed to the JID or LID
  field by server). **Guaranteed** from the protocol frame for a genuine reply;
  back-filled from the locally stored quoted message when the frame omits it.
- `quotedBody` — the quoted message's text/caption, from
  `ContextInfo.QuotedMessage`, truncated to 4096 bytes on a UTF-8 boundary.
  **Guaranteed** from the frame for text/caption replies; else the stored body.
- `quotedFromMe` — true when the quoted message was sent by this account.
  **Best-effort**: resolved authoritatively from the locally stored quoted
  message (the protocol frame has no reliable "quoted was mine" flag), so it is
  `false` when the quoted message predates local retention. The quote-enrichment
  stage runs in the inbound pipeline (after mention enrichment, before persist);
  the resolved fields are mirrored into `raw_json` when a repository supports that
  enrichment. Production gateways use `NoopRepos`: protocol-supplied quote fields
  remain available, but database-backed quote/mention enrichment is not wired there.

All quoted-* fields are `omitempty` and set only when `quotedMessageId` is present.

### Media policy (§11)

Sticker events additionally carry `sticker`, and replies can carry `quotedSticker`.
These contain the content hash, MIME type, availability status, and base64 bytes on
WebSocket delivery, replay, and webhooks. Stored events keep only references to the
globally deduplicated sticker store. See [shared sticker content](/docs/architecture/media-storage#shared-sticker-content).

Normalization extracts media metadata. The gateway adapter attaches a private descriptor for the API ingest transaction, which creates a capture job for linked sessions and removes the descriptor before public delivery. Upload completion emits `media.ready`; retention cleanup emits `media.expired`. See [attachment storage](/docs/architecture/media-storage).

### Ignore rules

`IgnoreRules` (built from the four `IGNORE_*` config bools via `IgnoreConfig`) classifies a
chat purely by its JID server, so it works on a bare string with no live client:

- `status@broadcast` → status (`IgnoreStatus`)
- `g.us` → group (`IgnoreGroups`)
- `newsletter` → channel (`IgnoreChannels`)
- `broadcast` (excluding the status JID) → broadcast list (`IgnoreBroadcast`)
- anything else → DM (never ignored)

`status@broadcast` is classified as **status**, not broadcast, so the two flags are
independent. An unparseable JID **fails open** (not ignored) — silently dropping
unclassifiable data is worse than persisting an odd JID downstream can still record.

`ClassifyChat` is exported and reused by the persistence layer to set `chats.type`.

### Decisions

- **No raw protobufs cross the package boundary.** Every nested proto is flattened into
  plain Go fields in the payload structs and `NormalizedMessage`.
- **`PersistResult` is the pipeline contract**, not the wire payload. It tags a
  `PersistKind` so the inbound pipeline dispatches without re-inspecting the event, and
  carries the parsed `*NormalizedMessage` for message-bearing kinds.
- **`session.status` payload.** `status`, `failureReason` (only with `failed`), `statusSeq`
  (orders a session's statuses; keep the highest), and with `reconnecting` the failed `attempt`
  count and `lastError`. The API projects a status only when its `statusSeq` is newer than the
  stored one; an event without `statusSeq` is left to the next desired-state report.
- **The session manager is the only `session.status` producer.** `Normalize` returns `ok=false`
  for connection lifecycle events. The manager reports a `Disconnected` as `reconnecting` only when
  the connection is still down after its grace period; `LoggedOut`/`StreamReplaced` are terminal
  → `logged_out`/`failed`.
- **Non-lifecycle receipts** (sender/retry/server-error/etc.) → `ok=false`.
- Poll **votes**: `events.Normalize` produces the target poll id only (the vote is still
  encrypted). The composition-layer `InboundNormalizer` then decrypts it via the live
  whatsmeow client (`cli.DecryptPollVote` → SHA-256 option hashes) and resolves those
  hashes to option text against the `polls` table (populated when the poll creation was
  persisted), writing `selectedOptions` onto both the `poll.vote` envelope and the
  `poll_votes` row. Poll vote persistence uses the normalized sender identity as the voter
  key: canonical LID when available, otherwise the sender phone JID. The key must be
  non-empty for a real vote so distinct voters do not collapse in replay de-dupe or recaps.
  An unresolvable hash (poll never seen) falls back to the raw hash.
  **Current production limitation:** `backend/cmd/gateway/main.go` passes a nil
  poll-options reader to `waadapter.NewInboundNormalizer`; the helper requires both
  that reader and a decryptor, and returns before decrypting when either is absent.
  Thus the helper's option-resolution behavior above is tested capability, not
  currently wired production behavior; do not assume incoming votes carry resolved
  selections or that recaps reconstruct those missing selections.
- Poll **recaps**: timed poll creation persists `polls.end_time` and schedules the close
  timestamp into a Redis sorted set for near-realtime wakeups. `PollRecapWorker` still uses
  MySQL as the source of truth: it sweeps due rows, claims `recap_emitted_at`, aggregates the
  latest vote per non-empty voter key from `poll_votes`, and emits one synthetic
  `poll.recap` event with option counts, total voters, `selectableCount`, `endTime`, and
  `hideVotes`. When `hideVotes=false`, the payload also includes a deterministic
  `voters` array sorted by stored voter key; each entry carries the voter key, the display
  name resolved at read time from `whatsapp_identities`, and the latest selected options.
  When `hideVotes=true`, `voters` is omitted entirely so the synthetic recap does not leak
  identities. Historical rows with an empty voter key are counted defensively as distinct
  rows rather than being merged under the empty string.

### How it's tested

Table-driven unit tests synthesize `*events.Message` values for each sub-type (text, text
from-me, group text, quoted+mentions, reaction, edit, revoke, location, contact, poll,
poll-vote, image/document media) and assert the mapped catalog `event`, `PersistKind`,
sub-type, persisted `type` string, and extracted fields (incl. the media
invariant). Separate tables cover receipts→status, session-status events, QR/pair, presence
+ chat-presence, group update vs participant, push-name/contact, call offer, newsletter, the
sender-LID-vs-PN rule, and the unknown-event drop. Ignore rules and `ClassifyChat` have
their own JID-classification tables. See the event normalizer tests for the complete cases.

## Transport (realtime + webhooks) — owned by another subsystem

Status: see `backend/internal/stream` and `backend/internal/webhooks` specs. Both carry the same
`domain.Event` envelope produced here. Since Increment 9 the **only** gateway-side
transport is the event journal: the gateway appends each envelope to its local
journal (no `event_log`, no Redis publication, no webhook enqueue — those
dependencies no longer exist on the gateway).

API-owned ingestion hands an envelope to
`application.CommittedEventConsumer` only **after** its event-log transaction
commits. The same transaction records explicit fan-out work in `event_fanout`
(migration 0030): one row per committed event with `status`
(`pending` → `leased` → `done` | `dead`), a per-claim `claim_token`,
`lease_until`, `attempts`, `next_attempt_at` and `last_error`.
`application.CommittedEventWorkStore` is the durable work boundary and
`service.CommittedEventWorker` drives it; its stateless
`CommittedEventDispatcher` runs registered projections (the API-side
WhatsApp-data projections), then realtime Redis publication, then webhook
enqueue in that order. Durable consumers must still use `event.id` as their
idempotency key because a crash can occur after a consumer accepts an event and
before completion is recorded.

**Ordering.** The API assigns every committed event a per-session
`session_seq` from `session_event_sequences` inside the committing transaction.
The sequence row lock serializes writers of one session until commit, so
`session_seq` follows commit order and, within one gateway batch, journal order
(the batch shares one `committed_at`, so neither the timestamp nor the event ULID
can order it). `gateway_ingested_events` also stores the gateway's
`journal_sequence` as provenance. Fan-out processes a session strictly in
`session_seq` order: only a session's **head** (its lowest `pending`/`leased`
row) is claimable, only when due, and only when no live lease holds it, so two
API replicas can never process one session at the same time. A claim leases up
to `Sessions` heads plus up to `PerSession - 1` contiguous successors each.

**Attempts and dead-letter.** An attempt is counted when it starts (`Start`
increments `attempts` and renews the per-event lease), so a worker that crashes
mid-event still uses an attempt. Every write after the claim (`Start`,
`Complete`, `Fail`, `Release`) is fenced by the claim token; a token is only
replaced by a new claim after its lease expired, so a matching token proves no
other claim took the event. A failed attempt returns the head to `pending` with
exponential backoff (1 s doubling, capped at 10 min) and releases the rest of
its session's claim, so the session waits behind it while unrelated sessions
continue. A permanent failure (`application.ErrPermanentEvent`: an undecodable
payload, a history event without a run id, or an event body missing from
`event_log`) or the 20th failed attempt (about two hours) moves the event to
`dead` with its `last_error`; the session then continues with its next event.
Every dead-lettered event is logged at error level with its event id, type,
session and error, and the worker logs the backlog (outstanding count, dead
count, oldest outstanding event with its attempts and last error) every minute
while either is non-zero. To replay a dead event after a fix, set its row back to
`status='pending', attempts=0, finished_at=NULL`.

**Sources.** Gateway events (`source='gateway'`) are projected and then
published. API-originated `message.from_me` events (`source='api'`) were
already projected by the outbound scheduler, so fan-out only publishes them and
enqueues webhooks; they go through the same durable path, so a crash after the
event-log append cannot lose their realtime or webhook delivery. Retention keeps
the event-log payload of every `pending`/`leased` fan-out row.


### Increment 5/9 durable handoff

Private-control gateways require an absolute `GATEWAY_JOURNAL_PATH` for a separate SQLite journal.
The journal accepts the normalized `domain.Event` JSON only while the current desired-state assignment
owns its organization/session (organization, epoch and live lease; the assignment's desired action
does not matter, so a session the API started with `ApplySession` keeps its first messages before
the RUN snapshot arrives), preserving that assignment epoch with the entry. It replays entries in
committed sequence order as protobuf `Struct` payloads over the control stream; exactly one batch is
in flight and the API acknowledgement must equal that batch's last journal sequence before deletion.
The API decodes each protobuf envelope, validates its identity against the control-frame metadata,
and stores only its inner type-specific JSON payload in `event_log.payload`. Committed-event
consumers reconstruct the envelope from the row columns; protobuf bytes or a nested envelope must
never enter that JSON column.
Each connection waits for a fresh, successfully applied complete desired-state
snapshot before replaying. An entry belonging to an assignment omitted from that
snapshot, or carrying a different assignment epoch/organization, is retired:
the API no longer authorizes that work. STOP assignments retain ownership and
keep their events. Same-assignment events survive reconnects with a fresh
connection epoch. A matching API ACK advances mixed batches; an entirely retired
prefix can advance locally under snapshot authority. Transient transport errors
never authorize deletion.

**One bad entry never blocks the journal.** Each entry gets its own verdict:

- On the gateway, an entry that cannot be decoded (or lacks its canonical
  assignment metadata), or that alone exceeds a control batch, moves to the
  local `journal_quarantine` table with its bytes and reason, is logged at error
  level, and replay continues with the next entry. Quarantined entries are kept
  30 days for repair.
- On the API, `IngestEvents` gives every entry of a batch a verdict, accepted or
  rejected with a reason. An envelope that cannot be decoded, or a payload whose
  media descriptor `media.Capture` cannot parse (`store.ErrGatewayEventInvalid`),
  is rolled back to its own savepoint (no dedupe row, outgoing-echo claim, event
  log or fan-out), recorded in `gateway_event_rejections` (migration 0031: ids,
  journal sequence, type, reason, payload size; never the payload, which can
  carry media keys), and logged. The batch commits and the cumulative ACK covers
  the rejected entry, so the gateway journal advances past it. A replay of the
  same batch is idempotent.
- `Unavailable` (the gateway reconnects and resends the batch) is returned only
  for a stale ownership fence or a real infrastructure failure (database,
  transaction). The ACK frame carries no per-entry verdicts: the protobuf
  `GatewayEventAck` keeps its reserved fields, and rejection details live on the
  API side.

Reconnects then replay the oldest remaining unacknowledged batch. A critical journal capacity state makes the gateway
unready, while a failed append backpressures the producing pipeline. Every heartbeat carries optional
journal-pressure telemetry (`journal_state`/`journal_entries`/`journal_bytes`, §7): an unreadable
journal omits the report instead of fabricating one, and the API persists the last reported pressure
on the registry row for admin observability. Paused/critical states are advisory to optional sync
work; no gateway sync work is pausable yet, so the seam is reserved, not exercised.

In control mode (the only mode since Increment 9) the gateway does
not append `event_log`, publish Redis events, or enqueue webhooks: API ingestion owns the single
event-log transaction and post-commit fan-out.
The API records successful API-originated sends in the outgoing message row, then appends a
`message.from_me` event and, in the same transaction, enqueues its durable fan-out
(`event_fanout`, `source='api'`); the committed-event worker publishes it to realtime and webhooks. WhatsApp may also echo the
same send through the gateway, including before the API finishes its own projection. API
publishing and gateway ingestion transactionally claim one public event owner by organization,
session, chat, and WhatsApp message ID in `outgoing_message_event_claims`. The first committed
claim retains its original public event ID and owns fan-out; later echoes are acknowledged in
`gateway_ingested_events` without another event-log row. A gateway-first echo is projected and
delivered by the committed-event worker, while the API outbox still records the send result.
Own messages sent from another linked device have no competing API outbox claim and still flow
through normal projection and delivery.
An echo of an API send completed before this claim table was introduced has no claim to match;
the one deployment needs a separately verified data upgrade before relying on deduplication
for those historical sends.
The event carries the send request's known content and WhatsApp acknowledgement timestamp;
stored media capture details may arrive separately.
Poll-recap emission is API-owned in every mode: the durable MySQL sweep and its event append,
realtime publish, and webhook enqueue run beside the committed-event worker on the API; the Redis
sorted set is only a low-latency wake-up index and gateways no longer write it.

## History sync events

When a device is linked or relinked, the phone sends the chat history it still has in
WhatsApp history-sync notifications. They never enter the live inbound pipeline: no
`message` / `message.from_me` events, no auto-read, no OAuth/admin interception, no
media or sticker capture. Instead the gateway emits two event types, both typed in
`backend/internal/apitypes/history.go`:

| event | payload | delivery |
|---|---|---|
| `history.sync` | `HistorySyncPayload`: `runId`, `phase` (`started` / `progress` / `completed` / `failed`), `accountJid`, `syncType`, `chunkOrder`, `progress` (phone-reported percent), `cutoffAt`, running counters `chunks` / `batches` / `conversations` / `messages` / `skipped`, `error` | like any event: matched by `*`, published to realtime, replayed by `since` |
| `history.batch` | `HistoryBatchPayload`: `runId`, `accountJid`, `syncType`, `chunkOrder`, `part` / `parts` (1-based split of one notification), `snapshotAt`, `conversations[]`, `contacts[]` | **bulk, opt-in only** (see below) |

A `HistoryConversation` carries the chat's phone-side state (`chatJid`, `type`, `name`,
`description`, `lid` / `phoneJid` for DMs, `unreadCount`, `archived`, `pinned`,
`mutedUntil`, `lastMessageAt`, group `participants[]` of `HistoryParticipant{lid,
phoneJid, role}`) plus its messages for this batch, **oldest first**. Each
`HistoryMessage` embeds the live `MessagePayload` (same field names and meaning) and
adds `kind` (the live event type the entry corresponds to), `status` (the recorded delivery status of an own message, applied on first insert
only) and `truncated`. `HistoryContact{lid, phoneJid, pushName}` carries push names and
phone-number-to-LID mappings. Conversation metadata repeats in every part that carries
its messages, so each batch is self-contained.

**Batch limits.** A batch holds at most 200 messages and about 96 KiB of JSON so it fits
webhook body limits; one oversized message gets its own batch (hard cap 768 KiB including
its conversation metadata, with `body` / `quotedBody` truncated and `truncated: true`
beyond that, so the event fits the gateway's 1 MiB journal replay batch).

**Gateway production.** `historysync.Convert` builds batches deterministically: messages
go through whatsmeow's `ParseWebMessage` and the same normalizer as live events (so the
`MessagePayload` is identical, media metadata only), sorted by (timestamp, `msgOrderID`).
It skips messages older than the cutoff, status updates (`status@broadcast`, status V3),
system notices and stub messages; a revoke stub becomes `message.revoked`, an edit
protocol message becomes `message.edited`, reactions and decrypted poll votes folded into
a message become `message.reaction` / `poll.vote`. Contacts come from push names, the
phone-number-to-LID mappings and conversation LID/PN pairs. Lifecycle: `started` before the
first chunk's batches, `progress` after each chunk, then `completed` or `failed` (see
[session manager: history sync](/docs/architecture/session-manager#history-sync-on-relink)).

**Bulk events are opt-in.** `domain.IsBulkEvent` (today only `history.batch`) is the one
rule every transport applies: a `*` webhook subscription or stream filter does not
match a bulk event (an exact `history.batch` element does), the realtime publisher
never publishes it, and event-log replay (`since` on the WebSocket and gRPC streams,
`GET` event listings) skips it. The row stays in `event_log` because webhook deliveries
read their body from it. Rationale: existing `*` receivers and live dashboards must not
start receiving large, high-volume bodies because history import shipped; the small
`history.sync` lifecycle is enough to show progress.

**API projection.** The API stores batches through `HistoryRepo` (insert-if-absent,
`origin='history'`, timestamp-seeded ids, fill-only identities, snapshot-aware unread
counts, no stale poll recaps) and tracks each run in `history_sync_runs`; see
[store: history projection](/docs/architecture/store#history-projection-historyrepo).
`HistoryMessage.kind` tells the projection (and webhook receivers) how to apply each
entry: `message` / `message.from_me` / `message.interactive_reply` become rows,
`message.edited` / `message.revoked` change `targetId`, `poll.vote` adds a vote, and
`message.reaction` stores nothing.

## Interactive selections

`message.interactive_reply` uses the message envelope with
`payload.interactiveReply: {kind: "button"|"list", id, title?}` and
`type: "interactive_reply"`. `quotedMessageId` identifies the original message
when supplied by WhatsApp. `chatJid`, `senderJid`/`senderLid`, and `fromMe` retain
normal message semantics, including group participants and linked-device echoes.
The event replaces the generic `message`/`message.from_me` event for that selection;
subscribe to it explicitly or use `*`. It travels through the existing webhook
and realtime transports and persists as a message with its normalized raw JSON.

Normalization accepts native-flow `quick_reply`/`single_select` responses and
legacy `ButtonsResponseMessage`/`ListResponseMessage`. Malformed JSON, missing IDs,
and unknown native flows remain unknown messages rather than fabricated selections.
IDs and display text are untrusted sender input. Applications correlate session,
chat, original message, and sender, then validate the ID against their own choices.
Typed numeric replies remain ordinary text messages; no selection state is held
by the gateway.

### Reading stored stickers

`GET /api/v1/sessions/{session}/chats/{cid}/messages/{message}/sticker` returns
the stored WebP descriptor and base64 content for an original message. It requires
read capability and joins the sticker reference to the caller's owned session,
with exact chat and message matching. The global blob hash alone grants no access.
Consumers can apply their own message-age retention before reading this endpoint.
