> **Increment 9: the gateway runs without MySQL or Redis.** The manager holds
> no session repository: `wa_sessions` rows, placement, assignments, status
> history, and admin bootstrap are all API-owned. Control-plane desired-state
> assignments are the only thing that starts a session locally, and every
> lifecycle event (status changes, pairing) flows to the API through the event
> journal for post-commit projection. The former MySQL-reading `Boot`, the boot
> orphan-guard, admin-number self-bootstrap, and `CreateSession` are removed.

Status: implemented. Package `backend/internal/wa`, files `manager.go`, `session.go`.

## Scope

Owns the in-process WhatsApp connection layer (§3, §5, §6): a `*whatsmeow.Client`
per assigned session, each holding a live WebSocket. Responsibilities:

- Materialize runtimes from **control-plane assignments** only: ownership,
  configuration, and device mapping all arrive in the revisioned assignment
  snapshot; the manager never reads `wa_sessions` or organizations.
- Drive pairing (QR and phone-number codes), reconnect with backoff + full
  jitter, and run the status state machine, emitting `session.status`,
  `auth.qr`, and `auth.code` through the event sink (the gateway journal).
- Forward every raw whatsmeow event to the injected inbound handler under a detached callback context. Production sets `InboundEventTimeout: 0` so
  journal backpressure can retain a critical event until it is durably recorded.

## gRPC control plane: API-owned lifecycle

The session lifecycle splits across the trust boundary:

- **The API owns durable state**: it picks the placement
  (`GatewayRepo.PickForPlacement`), inserts the `wa_sessions` row, its
  `wa_session_runtime` row (`stopped`, no observation) and the assignment at
  epoch 1 in one transaction (`GatewayAssignmentRepo.CreateSession`, which
  advances the owning gateway's desired revision), and deletes them on teardown.
- **Intent and observation are separate facts with one writer each.**
  - *Intent* lives on `wa_sessions`: `desired_state` (`run`/`stop`) and
    `start_generation`. Only user actions write it, through
    `SessionStateRepo.SetDesired` and `ClearPairing`: create with `start`,
    `:start`, `:stop`, `:restart`, `:logout`, and a pairing-code request. Start
    bumps the generation when the desired state was `stop` or the last run ended
    (failed, logged out, stopped); restart always bumps it.
  - *Observation* lives in `wa_session_runtime` (status, failure reason,
    `status_seq`, `status_changed_at`). Only the gateway writes it, through
    committed `session.status` events and through every desired-state report
    (`SessionStateRepo.ApplyObservedStatus` / `ApplyRuntimeReport`). A write
    applies only when its `status_seq` is newer than the stored one, so a late or
    replayed status never overwrites a newer one. A newer `logged_out` also clears
    the pairing identity.
  - The desired-state snapshot reads intent only (`desired_state`,
    `start_generation`, `wa_jid`, settings). A projected `failed` therefore no
    longer turns RUN into STOP, a late `stopped` no longer undoes a Start, and a
    pairing no longer makes a session RUN without a user action.
  - REST reads resolve the effective status at read time: a live observed status
    (`starting`, `scan_qr_code`, `working`, `reconnecting`) reads as
    `unavailable` while the session's gateway has no connected control stream
    (`gateways.connected_at IS NULL`, cleared by `DisconnectForEpoch`). Nothing is
    copied onto rows when a gateway goes away.
- **Pairing identity is API-projected.** The committed `auth.code` event
  (PairSuccess) is projected onto `wa_sessions` (`SessionStateRepo.AttachPairing`:
  `wa_jid`, `wa_lid`, phone derived from the JID). `wa_jid` is part of the
  snapshot, so attaching (and clearing) it advances the gateway's desired
  revision in the same transaction: a revision always names one snapshot content.
- **Applying intent now.** After recording intent, `:start`, `:stop` and
  `:restart` call the gateway's `ApplySession` RPC with the run flag, start
  generation and device JID, so the user does not wait up to one heartbeat for
  the next snapshot. The call is an accelerator: its failure is logged and the
  action still succeeds, because the snapshot carries the same intent. A
  pairing-code request records a run, applies it (this one must succeed) and then
  asks for the code on the running pairing connection.
- **Logout is a full pairing reset across the boundary.** The engine unlink runs
  as a durable command and must be confirmed by WhatsApp; then
  `SessionStateRepo.ClearPairing` clears `wa_jid`, `wa_lid` and `phone_number`
  and sets `desired_state=stop`, so the session stays logged out until a user
  starts it again. The gateway's `logged_out` status repeats the identity clear
  when it is projected.
- **GET /qr only reads.** `SessionService.QR` answers from intent and observation
  first: 409 for a paired session, a session not asked to run, a logged-out
  session, or a failed pairing (with `details.failureReason`); 503 when the
  gateway is not connected. Otherwise it reads the gateway's current code through
  `GetPairingQR` and answers `{state: "ready", code, expiresAt}` or
  `{state: "pending"}`. It never starts pairing; polling a failed session no
  longer reopens a doomed WhatsApp connection.
- **The gateway executes only live parts**, through private engine RPCs served
  by `wa.ApplicationGatewayAdapter` (see [`grpc-contracts.md`](/docs/architecture/grpc-contracts)):
  - `ApplySession` — runs (`Manager.StartAssigned` with the request's generation;
    settings stay those of the last snapshot) or stops (`StopAssigned`) a session
    behind the assignment fence.
  - `GetPairingQR` — reads the current QR code; never starts anything.
  - `PairPhone` — phone-number pairing on the running pairing connection (it
    starts the pairing run itself when none runs).
  - `SubmitPasskey` / `ConfirmPasskey` — passkey steps of a running pairing.
  - `LogoutSession` — destructive unlink as a durable command with full send-style
    ledger replay (records `CommandSent` only). It accepts a stopped session
    under the same organization/epoch/lease assignment fence.
  - `ForgetSession` — in-memory runtime drop during delete; idempotent, no epoch
    requirement (the row may already be deleted API-side).
  - `PrepareSession` and `BeginPairing` are deprecated and answer `Unimplemented`;
    they stay in the proto only so the contract remains additive.
- Delete order: OAuth cascade → engine forget → repo delete (the assignment and
  runtime rows cascade). Logout order: engine logout → pairing clear → OAuth
  cascade.
- **Registry writes are gone from the gateway.** There is no `joining`/`active`
  registration, no heartbeat timer, and no shutdown draining/drained write to
  `wa_gateways`: liveness is the acknowledged control-stream heartbeat itself.
- **Boot and drain.** All engine admission stays closed until a RUN+READY
  heartbeat is durably acknowledged. A DRAIN directive stops sessions terminally
  via `Manager.Shutdown` and reports DRAINING/DRAINED; a later RUN after terminal
  drain reports BUSY instead of rebooting sessions. A transient pre-Welcome
  outage brings diagnostics up unready, then performs the deferred start after a
  RUN Welcome. Startup accepts an applied snapshot from a newer connection after
  reconnect and returns terminal control errors instead of waiting indefinitely.
  On SIGTERM the supervisor flushes acknowledged DRAINING/DRAINED
  heartbeats before its stream is cancelled. Those are observed states and do
  not change the separate desired lifecycle.
- **No orphan-guard and no admin bootstrap on the gateway.** Assignment
  reconciliation replaces the org-existence guard: an org deletion removes the
  session's assignment, and reconciliation stops it. Admin session creation,
  pairing kickoff, and status persistence are API operations executed over the
  same engine RPCs as any other session.

## WhatsApp client version

WhatsApp rejects clients whose version falls too far behind with `ClientOutdated` (405); every
session then fails until the gateway is upgraded. This happened from 2026-10-26 until the
whatsmeow upgrade on 2026-11-23. At boot, before any session connects, the gateway reads WhatsApp
Web's current client version (`whatsmeow.GetLatestVersion`) and adopts it with
`store.SetWAVersion` when it is newer than the compiled one. A failed fetch keeps the compiled
version. It runs only at boot because `SetWAVersion` writes a package global that connecting
clients read without a lock. It does not replace whatsmeow upgrades, which a protocol change
still needs. Fake-WhatsApp mode skips it.

## Pairing recovery

The gateway does not use whatsmeow's `GetQRChannel`. That channel disconnects the client as soon
as its QR codes run out, which would end a passkey verification still in progress, and it
confirms passkey pairings by itself. The manager's pairing driver (`internal/wa/pairing.go`)
handles the raw events instead:

- `events.QR` starts an emitter that stores each code for `GET /qr`, publishes it as `auth.qr`
  (60 s for the first code, 20 s for the rest) and replaces the ADV secret in the remaining codes
  on `events.RotateADVSecret`. When the codes run out the session fails with `qr_timeout`, unless
  a passkey verification is pending. A passkey request or `PairSuccess` stops the emitter for good
  (a per-run stop channel): left running, it published `scan_qr_code` over a working session and
  tore the paired client down with `qr_timeout` once its codes ran out.
- The status moves to `scan_qr_code` only once there is something to scan or enter: after the
  first QR code is stored, or after WhatsApp returns a phone-number pairing code. Until then the
  session keeps its previous status.

### Passkey verification

WhatsApp asks accounts that have a passkey to sign a WebAuthn challenge before it links a new
device, after a QR scan or a phone-number code alike. Removing the passkey from the account does
not stop it. WebAuthn only accepts WhatsApp's own origin for the `whatsapp.com` relying party, so
neither the gateway nor the dashboard can request the signature. The user signs it on
`web.whatsapp.com`:

1. `events.PairPasskeyRequest` stops the QR codes (WhatsApp rotates the ADV secret, so the old
   codes are dead), records the request on the managed session and publishes `auth.passkey` with
   `step: verify`, the WebAuthn request options in `publicKey`, and `expiresAt`. The connection
   stays open until the verification completes, fails, or passes `expiresAt`: the larger of
   3 minutes and the options' timeout, capped at 10 minutes. After that the session fails with
   `passkey_failed`.
2. The dashboard gives the user a script to paste into the console on `web.whatsapp.com`. It adds
   a button (a passkey prompt needs a click on a focused page), calls
   `navigator.credentials.get()` with the options, and copies the credential JSON. The user pastes
   it into the dashboard, which sends it to `POST /sessions/{session}/passkey`; the engine RPC
   `SubmitPasskey` passes it to whatsmeow's `SendPasskeyResponse`. A rejected assertion leaves the
   verification pending.
3. `events.PairPasskeyConfirmation` either confirms by itself (`SkipHandoffUX`, when the QR scan
   already proved the handoff) or publishes `auth.passkey` with `step: confirm` and the `code` to
   compare with the phone. `POST /sessions/{session}/passkey/confirm` (engine RPC
   `ConfirmPasskey`) sends `SendPasskeyConfirmation`. `PairSuccess` follows.
4. `events.PairPasskeyError` fails the session with `passkey_failed`.

### Failure reasons

Every failed status carries a `failureReason` in the `session.status` payload. Pairing can end
with `qr_timeout`, `passkey_failed`, `pairing_error` (WhatsApp rejected the handshake:
`events.PairError`, or a failed code request on a fresh connection) or `connect_error` (the
gateway could not open the pairing connection).

Starting an unpaired session always opens a QR flow. A phone-number pairing request while
that flow runs asks for the code on the same connection (whatsmeow's `PairPhone` runs on a
connected pairing client, which also receives QR codes) instead of refusing with a conflict.
A failed code request leaves the QR flow running.

Gateway conflicts keep their own message across the engine RPC: the gateway returns
`FailedPrecondition` with the domain error's message and the API returns it as `409 conflict`.

Phone-number pairing sends the fixed companion name `Chrome (Linux)`. WhatsApp validates it as
`Browser (OS)` with a common browser and OS and answers `400 bad-request` otherwise, so the
configured device name (shown in the phone's Linked devices list through `store.SetOSInfo`)
cannot be used there.

The failed status is published with a context that ending the run cannot cancel, because failure
paths end the run before they record the status.

QR timeout marks the session failed, ends its run (reconnect driver, event handler and client),
and clears the cached QR. A subsequent pairing request creates a fresh run instead of reusing
an exhausted QR channel. Stopping a flow and successful QR pairing also clear its cache, and
QR reads never return a code after its expiry. A reconnect of an unpaired run receives a new set
of QR codes; their emitter replaces the previous one.

## Connection runs and reconnects

Each start of a session creates one **run** (`connection` in `internal/wa/session.go`): one
whatsmeow client, its registered event handler, one reconnect driver goroutine, and the run's
QR emitter and passkey deadline. A run has a generation number within its session, and every
callback carries the run it belongs to:

- The event handler skips lifecycle handling for events of a run that is no longer current. A
  late `Connected`, `LoggedOut` or `StreamReplaced` from a torn-down client therefore cannot mark
  a stopped session working or end the newer run. Data events of an old run (messages that arrived
  just before a stop) still reach the inbound pipeline, whose sink checks ownership.
- Ending a run cancels its context, unregisters its event handler (`RemoveEventHandler`, part of
  the client interface) and disconnects the client. whatsmeow forbids removing a handler from
  inside a handler, so a terminal event closes the client on a separate goroutine; the context
  is cancelled first, which already stops the run's goroutines.
- QR emitter, passkey deadline and automatic passkey confirmation end the run they were started
  for and do nothing if that run is already over.

**One reconnect driver.** The manager drives every reconnect; `buildClient` turns whatsmeow's
`EnableAutoReconnect` off for every client, because two drivers race each other's `Connect`
calls. The driver connects, then waits for the transport to drop: a `Disconnected` event, a
keepalive failing for more than three minutes (whatsmeow only forces that reconnect when its own
reconnect is on, so the manager does it), or a liveness check every 5 seconds that finds no socket
(drops that emit no event, such as a failed reconnect after the post-pairing `515` restart).
`ErrAlreadyConnected` from `Connect` means the socket is up and counts as success. Retries use
`backoffFor` (1s base, ×2, cap 2m, full jitter).

**Bounded retries.** Consecutive failed attempts without a `Connected` event in between are
counted. After `MaxConnectAttempts` (default 10) the run ends as `failed` with
`failureReason: connect_error`. A connection WhatsApp will keep refusing (an HTTP status other
than 408 or 5xx, or a deleted device) ends the run at once as `failed` with `connect_rejected`.

**Reconnect grace period.** WhatsApp drops connections several times a day and they come back
within one or two seconds. The status stays `working` while the transport is down; only when it
is still down after `ReconnectGrace` (default 10 seconds) does the session report `reconnecting`,
with the failed `attempt` count and the `lastError`. A run that never connected stays `starting`.
A drop that recovers within the grace period publishes nothing, so users and webhooks do not
see an outage that did not happen. The session reports `working` again on the next `Connected`.

**Serialized lifecycle operations.** Every lifecycle operation on a session (start, stop,
QR and phone pairing, logout, forget, assignment start/stop) holds the session's operation lock
for its whole duration, so two operations never interleave their read-then-act steps (for
example a logout racing a QR start). Event callbacks never take that lock; they identify their
run instead. The state lock is held only for short reads and writes, never across network calls.

**Logout reports failure.** Unlinking is a request to WhatsApp, so it needs a logged-in
connection: logging out a stopped paired session connects it for the duration of the call. When
WhatsApp does not confirm the unlink, `Logout` returns the error and keeps the device paired, so
the caller can retry; it no longer reports success while the device stays linked on the phone.
An unpaired session has nothing to unlink and is marked logged out.

**Live operations need a working session.** Live operations (groups, contacts, presence, read
receipts) read readiness from the session's status, not from the presence of a client. A session
that is not `working` answers `503 gateway_unavailable` with `details.reason: session_not_ready`
and the current status; the engine RPC carries it as gRPC `Unavailable` and the API keeps the
message. `501 not_implemented` is reserved for client types that cannot perform the operation.

**Single status producer.** Only the manager publishes `session.status`. The inbound normalizer
no longer turns `Connected`, `Disconnected` or `LoggedOut` into status events; a second,
undebounced producer contradicted the manager (for example a `starting` for every transient drop).

## Start generations, the failure latch and runtime reports

**Unpaired RUN is pairing.** A RUN assignment without a device JID asks the
gateway to run QR pairing: `StartAssigned` registers the session with a fresh
unpaired device and starts a pairing run. This is also how interrupted pairing
resumes: after a gateway restart, the next snapshot still says RUN without a
device, so the gateway starts a new pairing run (new QR codes) instead of leaving
the row `starting` forever. Resuming was chosen over ending the pairing because
the user asked for the session to run and has not changed that; a resumed pairing
nobody scans ends as `failed` with `qr_timeout` after its codes run out.

**Start generations.** Each assignment carries `start_generation`, which the API
bumps for every explicit start or restart. `StartAssigned` compares it with the
generation of the session's current or last run:

| Assignment generation | Effect |
|---|---|
| older | stale request, ignored |
| newer | the user asked again: a running session restarts, a failed or logged-out one starts |
| equal | starts only when the session is neither running nor latched |

**Failure latch.** A run that ends terminally (`failed`, `logged_out`) latches the
session. Heartbeat snapshots repeat the same generation, so they never restart a
latched session: a `stream_replaced`, `temporary_ban` or `client_outdated` session
stays failed instead of reconnecting within seconds and erasing the failure. They
do resume a session stopped by lease expiry, which is not latched. `StopAssigned`
leaves a latched session's status alone. The latch is in memory: after a gateway
restart every RUN session gets one new attempt.

**Status sequence.** Every published status carries `statusSeq` from a hybrid
logical clock (`Manager.nextSeq`): wall-clock milliseconds × 1000, or the previous
value + 1 when that is not larger. It increases strictly within the process, a
restarted gateway starts above its previous process's values, and it stays below
2^53 so JavaScript clients read it exactly. A reassignment resets the stored
sequence, since sequences of different gateways are not comparable.

**Runtime in every report.** Each desired-state report carries the observed
runtime (status, failure reason, `statusSeq`, change time) of every assigned
session (`desiredstate.Runtime.SessionRuntime`). A session this process never
touched reads as `stopped` at the process's boot sequence. The API stores every
entry that is newer than what it has, fenced by connection epoch and assignment.
A status event the sink dropped (assignment not live yet), the journal replay
skipped (older epoch), or `setState` never emitted is therefore repaired within
one heartbeat.

**Fresh pairings are not unexpected devices.** The inventory reports the paired
device each managed session holds. A RUN assignment without a device whose
session already holds one (it paired after the snapshot was built) reports that
device as its result, so it is not classified `unexpected_local_device` and the
gateway does not turn `degraded`. The API accepts that result while the row has
no `wa_jid`; a report for a superseded revision is skipped instead of resetting
the control stream.

## Desired-state assignment foundation

After authenticated connection, the API emits a complete revisioned assignment snapshot, and emits
a fresh snapshot after every durably persisted heartbeat to renew leases. Each assignment includes
the organization ID, nonzero durable `assignment_epoch`, absolute lease expiry, and the session's
auto-read, typing, rate, and history-import (`HistorySyncDays`, carried in
`desiredstate.Config`) settings. The gateway acknowledges the applied snapshot revision; the
API persists that acknowledgement only for the still-current connection epoch and desired revision.
Reconciliation stops unassigned or expired sessions and carries the epoch on all commands and events.
Stopped assignments retain ownership of pairing and lifecycle events, so a phone-code or QR
pairing attempt can project its paired identity and connection status before desired run is
enabled. Message and resource events still require a running assignment; organization,
assignment epoch, and lease fencing apply to both paths.
An unchanged stopped assignment does not tear down an in-progress pairing flow when a lease
renewal snapshot arrives. A transition from running to stopped, a changed owner or epoch,
omission, or lease expiry stops the local runtime.
An explicit Stop of an unpaired session first forgets its live pairing client, then persists
the stopped state; the snapshot alone cannot distinguish Stop from an ongoing pairing flow
because both have no paired device JID.
Later QR and phone-code requests prepare the local device again before starting their new flow.
Reconciliation stores a NULL device JID for each unpaired STOP result, so several unpaired
sessions can share a gateway while the unique device fence still applies to paired identities.
The reconciler publishes each candidate assignment set before invoking runtime start/stop callbacks,
so synchronous status publication can validate the new epoch without taking the reconciler lock
recursively. Runtime callbacks run outside the state lock and are serialized as one transaction;
if a callback fails, the reconciler stops every prior or candidate runtime it could have touched,
then clears ownership while retaining the previous revision for retry. Lease expiry removes each
expired assignment first, attempts every corresponding runtime stop, and fails closed if any stop
fails.

## History sync on (re)link

When a device is linked, the phone uploads the chat history it still has and sends one
history-sync notification per chunk. The gateway imports it durably; package
`backend/internal/gateway/historysync`.

**Manual download.** Every client the manager builds (QR, phone code and reconnect all go
through `Manager.buildClient`) runs whatsmeow in manual history mode:
`ManualHistorySyncDownload` and `DisableManualHistorySyncReceipt` are set, so whatsmeow
neither downloads nor acknowledges history itself. Rationale: whatsmeow's default sends the
receipt first and downloads on a goroutine with no durability, and a slow handler stalls the
live event loop.

**Interception.** The manager's event handler recognizes the history-sync protocol message
(`ProtocolMessage.historySyncNotification` on an own message) **before** the status state
machine and the inbound pipeline. It never auto-reads, never reaches the OAuth/admin
interceptors and never becomes a `message` event. `HistoryInbox.Accept` inserts the
notification into the `history_inbox` table of the journal SQLite
(`UNIQUE(session_id, notification_id)`), and only then sends the `hist_sync` receipt. A
failed insert leaves the notification unacknowledged so the phone sends it again. The
cutoff (`now − historySyncDays`) and whether the import is on are fixed at that moment.
`historySyncDays` is read from the session's current assignment in the reconciler, which
exists (stopped) while a new device is still pairing, before the runtime has started it.

**Worker.** One `historysync.Worker` per gateway drains the inbox in arrival order per
session (`GATEWAY_HISTORY_CONCURRENCY` sessions at once, default 1). It starts only after
the first desired-state snapshot is applied. For each notification it:

1. discards it when the session is no longer on this gateway or the device now belongs to a
   different account; postpones it while the session is disconnected or not owned;
2. calls `DownloadHistorySync(ctx, notif, true)`. This runs even when the import is off
   (`historySyncDays = 0`), because whatsmeow stores message secrets, LID mappings and push
   names from the blob; nothing is journaled in that case;
3. on 404/410 sends one `SendHistorySyncServerErrorReceipt` (the phone may re-upload as a
   new notification) and marks the notification failed; on other network errors retries
   with backoff (5 s doubling, at most 10 min) for up to 24 h, then fails the run;
4. converts the blob with `historysync.Convert` and journals the `history.batch` events
   from a persisted cursor (`batches_done`), about 4 per second per session, pausing while
   the journal is not in its healthy capacity band;
5. journals a `history.sync` `progress` event, adds the counters to the run in the same
   transaction that marks the notification done, then deletes the blob from the media
   server (best effort).

Event ids are deterministic ULIDs (notification time, entropy `sha256(session |
notification | batch index)`), so re-processing after a crash re-appends the same ids and
the journal deduplicates them.

**Runs.** A run (`history_runs`) groups the notifications of one account. It is created by
the first processed notification, which journals `started`. It completes when a `RECENT`
notification reports 100% (`FULL` when full sync is enabled) and nothing is pending, or after
10 minutes without a notification; it fails when a download gives up or the session is
relinked or logged out. The final `completed`/`failed` event is journaled from the run
table, so it survives restarts. `PairSuccess` discards pending notifications and fails the
running run of any other account; logout and `Forget` discard everything pending.

**Full sync (operator opt-in).** `GATEWAY_HISTORY_FULL_SYNC=true` asks the phone for full
history, capped at `GATEWAY_HISTORY_FULL_SYNC_MAX_MB` (default 256). It sets
`Client.GetClientPayload` to patch a **clone** of whatsmeow's process-global
`store.DeviceProps` (`requireFullSync`, `fullSyncSizeMbLimit`) for registration payloads
only; the global is never mutated, and paired devices log in unchanged.

`historysync.Client` is the narrow client slice the pipeline uses (`DownloadHistorySync`,
`ParseWebMessage`, `SendProtocolMessageReceipt`, `SendHistorySyncServerErrorReceipt`,
`DeleteMedia`); `*whatsmeow.Client` and the development fake both satisfy it, and
`Manager.HistoryClient` hands the worker the connected one.

## Key types / interfaces

Consumer interfaces (defined here; the composition root wires concrete types — no
sibling internal imports):

- `Keystore` — slice of the whatsmeow device container
  (`GetAllDevices/GetFirstDevice/GetDevice/NewDevice/DeleteDevice`). Satisfied by
  the gateway-local SQLite keystore (`modernc.org/sqlite`, §6.1). Uses the external
  `store.Device` type, which is allowed.
- `EventSink` — `Publish(ctx, domain.Event)`; the manager only emits
  `session.status`, `auth.qr`, `auth.code`.
- `InboundHandler` — `Handle(ctx, sessionID, organizationID, isAdmin, evt any)`;
  every whatsmeow event is forwarded with the configured callback context.
- `Clock` — `NowMs()`; defaults to `domain.NowMs()`.
- `waClient` (unexported) — the narrow slice of `*whatsmeow.Client` the session
  drives (`Connect/Disconnect/IsConnected/IsLoggedIn/Logout/AddEventHandler/
  GetQRChannel/PairPhone`). The real client satisfies it (compile-time assert);
  tests inject a fake, so the full lifecycle is exercised without a WebSocket.
  Built via a swappable `clientFactory` (`SetClientFactory`). The exported `Client`
  alias lets development and the API/gateway E2E suite supply the shared
  `internal/fakewhatsapp` client while running the actual `Manager` against a
  gateway-local SQLite device store. The standalone `cmd/fake-whatsapp` server
  owns simulated phones, scenarios, and remote effects; the client translates
  its HTTP protocol into whatsmeow lifecycle and message events.

### Development WhatsApp actor

`WHATSAPP_FAKE_SERVER=true` selects the remote simulator for lifecycle, live
operations, and outbound transport. `WHATSAPP_FAKE_SERVER_URL` selects the
server, and `WHATSAPP_FAKE_STORE_DSN` selects a separate local SQLite identity
store. An unavailable simulator produces a connection failure; there is no
fallback to the live WhatsApp service.

Phone numbers beginning with `555` identify simulated phones. Scenarios are
explicit server state configured through its development panel or HTTP API.
Reusable presets are typed Go scenario definitions registered in the fake package.
The panel discovers the catalog over HTTP and runs ordered group, message,
effect, and configuration steps against the selected phone. Run results retain
completed effects and identify any failed step; they report gateway delivery
separately from creation of a fake transcript entry.
Pairing uses the normal API and manager flow, with approval supplied by the
simulated peer. Successful pairing persists the fake JID/LID in SQLite before
emitting lifecycle events, so gateway restarts exercise normal device recovery.

History sync is simulated at the same boundary. With `history_sync` in the phone's
config (or `POST /v1/numbers/{number}/history`), the peer sends history-sync protocol
messages as an own message: an `INITIAL_BOOTSTRAP` notification with a zlib-compressed
inline payload built from the phone's transcripts (or a seeded conversation), then
`RECENT` notifications (10 chats each, the last at 100%) whose blobs the client downloads
from the peer; `history_chats` × `history_messages` adds synthetic chats and
`history_404` expires the downloadable blobs. The fake client implements
`historysync.Client`: it fetches downloadable blobs, then lets its local whatsmeow client
inflate, decode and store them, and records receipts, server-error receipts and
`DeleteMedia` as peer operations. The `large-history` (50 chats × 400 messages) and
`expired-history` scenarios exercise volume and the 404 path.

This boundary preserves gateway lifecycle, assignment fencing, inbound handling,
outbound protobuf construction, and journal/control-plane processing. It does
not implement WhatsApp's encrypted network protocol. Internal API/gRPC fault
controls stay in their existing E2E harness; WhatsApp faults use the shared
simulator without a parallel test-only device implementation. See
[local development](/docs/operators/local-development#develop-without-a-real-whatsapp-number)
for startup and pairing.

The hostile environment is organized by the observable WhatsApp boundary:

| Failure family | Controlled peer behavior | Evidence to inspect |
|---|---|---|
| Pairing and identity | Pending approval, rejected fake identity, linked device reconnect | Public session status and persisted device recovery. |
| Connection lifecycle | Refused connection, disconnect, logout, replaced stream, terminal connection failure | Session state, reconnect behavior, and a subsequent valid operation. |
| Outbound acceptance | Reject before commit, hold a send until released, cancel a blocked request | Transport attempts versus the peer's committed message transcript. |
| Ambiguous acknowledgement | Commit the message and lose its acknowledgement | Recipient transcript and the API's eventual command outcome, without assuming stronger WhatsApp deduplication guarantees. |
| Upload and download | Reject media transfer independently of message send | No message committed from a failed upload; successful transfer after recovery. |
| Inbound ordering | Duplicate messages, own echoes, stale or reordered receipts | Public message history and event delivery after projection. |
| Capacity and concurrency | Caller-configured event bursts and paused sends | Accepted event identities, committed effects, and progress after pressure is removed. |

Scenarios specify initial state, trigger, exact fault schedule, recovery action,
and observable invariant before implementation. Barriers establish causal order;
user-selected burst counts and pacing are workload inputs, not inferred product
limits. The E2E artifact records executed results; this inventory is not a claim
that every WhatsApp protocol failure has been reproduced. Network encryption,
WhatsApp's changing service policy, and upstream protocol compatibility remain
outside the simulated client boundary.

Core types:

- `Manager` — `map[sessionID]*ManagedSession` under `sync.RWMutex`; constructor
  `NewManager(keystore, repo, sink, inbound, clock, log, cfg)` where `repo` is
  deprecated plumbing that must be nil (the gateway owns no rows). `StartAssigned`
  materializes one assignment; `StartAssignedBoot` is the store-free boot hook;
  `StopAssigned` stops a locally materialized assignment.
- `ManagedSession` — wraps the device, the current run (`connection`), status and failure
  reason, the attempt count of the current run, plus the JID/LID observed at `PairSuccess`.
  An operation lock serializes lifecycle operations; a state lock guards the fields.
- `Config` — `GatewayID`, device display name, rate/auto-read defaults, optional
  backoff.

## Decisions

- **Pure cores for testability.** Three pure functions carry the load-bearing
  logic and are unit-tested directly:
  - `classifyEvent(evt any) transition` — maps a whatsmeow event to
    `(status, changed, terminal)`. `Connected→WORKING`,
    `PairSuccess→STARTING`, terminal events→`FAILED`/`LOGGED_OUT` and end the run. A `FAILED` transition carries its reason (`stream_replaced`,
    `temporary_ban`, `client_outdated`, `pairing_error`, `passkey_failed`, `connect_rejected`); `Disconnected` and transient `ConnectFailure` cause no status change
    (the reconnect driver retries and reports after the grace period).
  - `isFatalConnectFailure(reason)` — distinguishes permanent
    (logged-out/banned/locked/outdated/bad-UA) from transient connect failures.
  - `backoffFor(cfg, attempt, *rand.Rand)` — exponential `base*factor^n` clamped
    to `max`, then **full jitter** (`uniform[0, ceiling]`). Deterministic given a
    seeded `*rand.Rand`. Production default: 1s base, ×2, cap 2m.
- **Status ownership is single-writer.** `setState` (and `endRun` for terminal outcomes) is the
  sole owner of the status field and its `session.status` emission, and it **dedups** (no event
  when the status and failure reason are unchanged). A state change for a run that is no longer
  current is ignored. Persistence is derived API-side from committed events. Logout is the
  intentional specialized path: ending a run as logged out swaps in a fresh unpaired device,
  clears the QR cache, and **always emits** `session.status=logged_out` — even when the
  in-memory status was already logged_out — because that event is the durable signal the API
  projection uses to repeat its row clear.
- **Goroutine lifecycle.** Each run owns a context. Stop, Logout, Forget, Shutdown and terminal
  outcomes cancel it; the reconnect driver, QR emitter and passkey deadline select on it and
  exit cleanly.
- **Pairing / linked-device display name** defaults to `"Chrome (Linux - <GATEWAY_ID>)"` and can
  override the OS/app portion with `WHATSAPP_DEVICE_NAME`. The phone-code pairing string is still
  formatted as `"Chrome (<device name>)"` because whatsmeow validates the `"Browser (OS)"` format.
- **whatsmeow is imported directly** (external module): `whatsmeow`, `/store`,
  `/types`, `/types/events`, `/util/log`. No sibling internal packages.

## How it's tested

`session_test.go` + `manager_test.go`, table-driven, all boundaries faked:

- `classifyEvent` across every relevant event incl. fatal vs transient
  `ConnectFailure`; `isFatalConnectFailure` matrix.
- `backoffFor`: determinism (same seed → same schedule), full-jitter bounds
  per attempt, cap never exceeded, negative attempt clamped.
- Status dedup; a terminal event ends the run (handler unregistered, client closed), emits,
  and still forwards to inbound; `Connected` resets the attempt count; `PairSuccess` records
  the JID/LID onto the managed session.
- Runs: events of a replaced run change nothing (`TestStaleRunEventsAreDropped`); whatsmeow
  auto-reconnect is off on built clients; `ErrAlreadyConnected` is success; exhausted attempts
  fail with `connect_error`; a refusal fails at once with `connect_rejected`; a drop within the
  grace period publishes nothing and a longer one publishes `reconnecting` then `working`; lifecycle
  operations wait for each other; a failed unlink fails `Logout` and keeps the device; live
  operations on a non-working session answer `session_not_ready`.
- Online presence: the manager announces `PresenceAvailable` on `Connected`, but
  whatsmeow's `SendPresence` requires a push name that only arrives via app-state
  sync (after `Connected`) — so it re-announces on `AppStateSyncComplete`, which is
  when presence actually sticks on a freshly-paired session. A missing push name is
  benign (debug-logged, retried), not a warning.
- Lifecycle: `StartAssigned` uses control config without any session lookup;
  QR starts are idempotent while the pairing runs; `StopAssigned` ends the run and emits
  STOPPED; `Logout` calls `client.Logout` (connecting a stopped session first), deletes the
  keystore device, installs a fresh unpaired device, and can immediately begin a new
  pairing-code flow;
  external `LoggedOut` performs the same reset; not-found errors;
  `StartAssignedBoot` is store-free; the manager accepts no session repository.

Verified: `CGO_ENABLED=0 go -C backend build ./internal/wa`, `go -C backend test ./internal/wa` (incl.
`-race`), `go -C backend vet ./internal/wa` all pass.

Creation and deletion use the store's session lifecycle transactions: the session,

remain explicit engine operations outside MySQL; see [`store.md`](/docs/architecture/store).
