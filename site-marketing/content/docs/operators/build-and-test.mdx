The [WhatsApp Gateway source repository](https://github.com/rama-adi/quick-whatsapp-gateway) has a Go backend (API and gateway processes), the `web/` dashboard,
and the `site-marketing/` marketing and documentation app. Each has its own set
of commands that must succeed before a change lands. The backend and dashboard must pass at every commit,
not just at the end of a branch.

## Gateway (Go)

Run all three from the WhatsApp Gateway checkout directory (the directory containing `Makefile`):

```sh
go -C backend build ./...
go -C backend vet ./...
go -C backend test ./...
```

| Command | What it checks |
|---|---|
| `go -C backend build ./...` | Everything compiles. |
| `go -C backend vet ./...` | Static checks for common mistakes (bad format strings, unreachable code, and similar). |
| `go -C backend test ./...` | The full test suite. |

The build and tests run with `CGO_ENABLED=0` because the gateway uses a pure-Go SQLite
driver (no C compiler needed).

### API and gateway process E2E

Run the API/gateway E2E suite from the repository root with Docker running:

```sh
make api-e2e
```

The opt-in `TestOutboundE2E` starts disposable MySQL and Redis containers on
loopback ports, migrates a fresh database, and launches the real API composition
and a gateway process with its real Manager, SQLite device store, and private
engine. The gateway substitutes the external WhatsApp client transport for
connectivity, pairing, contacts, groups, media, and sends.
It exercises HTTP, public gRPC, and private gateway traffic without contacting WhatsApp or an existing deployment.
The test cleans up its containers and child processes when it finishes.

The [coverage inventory](https://github.com/rama-adi/quick-whatsapp-gateway/blob/main/backend/cmd/api/e2e-coverage.json)
lists each OpenAPI operation, direct router/OAuth route, and public gRPC RPC as
covered by a named successful E2E scenario or verified to return its documented
`501` response. `make api-e2e-coverage-check`
compares that inventory with `docs/openapi.yaml`, direct route registrations, and the public protobuf services;
it fails when a new operation or route has no entry or any operation remains untested. An inventory entry describes
what the E2E suite asserts, rather than claiming coverage from authentication
or package tests alone. The same check and E2E command run in CI for backend and
API contract changes.

The isolated external-service fixtures use HTTPS and replace only the S3 network
transport; the AWS request signer, media jobs, gateway download RPC, and storage
queries remain real. The suite rejects storage requests before recovery, verifies
token isolation and expiry, and verifies signed webhook retries over HTTP.

### Repeatable E2E evidence

`make api-e2e` writes a fresh directory under `.artifacts/api-e2e/` and prints
the path to `result.json`. The runner preserves raw Go test events and a result manifest, including
source hashes, tool versions, the command, scenario outcomes, and evidence checksums.
A fresh artifact directory identifies each run. CI uploads the evidence even when
the run fails. Re-run the recorded command against the recorded source to reproduce
the scenarios; timing, generated IDs, and temporary ports are not expected to match.
For an uncommitted checkout, `changes.patch` and `untracked.zip` preserve the edits
alongside the base commit in `source.json`. To reconstruct it, check out that commit
in a separate worktree, apply `changes.patch` if nonempty, and extract `untracked.zip`
there. Verify the reconstructed files against the hashes in `source.json` before
running `make api-e2e`. The image digests and tool versions are recorded in `result.json`.

Verify a run's evidence checksums with its printed directory:

```sh
python3 - /absolute/path/to/.artifacts/api-e2e/run-directory <<'PY'
import hashlib, json, pathlib, sys
root = pathlib.Path(sys.argv[1])
for name, expected in json.loads((root / "checksums.json").read_text()).items():
    assert hashlib.sha256((root / name).read_bytes()).hexdigest() == expected, name
result = json.loads((root / "result.json").read_text())
assert result["status"] == "passed", result["errors"]
print("Evidence checksums verified; recorded E2E result passed")
PY
```

Before implementing this runner, its failure cases are: the coverage inventory
fails; Go fails to compile or exits unsuccessfully; the selected suite is skipped
or absent; a scenario fails; the process cannot start; output is not valid test
JSON; writing evidence fails; and source changes during execution. None of these
may produce a passing manifest. A test failure must still leave the available raw
evidence and a failing result. Checksums verify evidence integrity, not independent
proof that a claimed result is truthful.

### Contract tests for auth formats

The router accepts two better-auth formats: api-keys and EdDSA JWTs (signed JSON
tokens that carry the caller's identity). If better-auth changes how it stores an
api-key hash or shapes a JWT, callers could stop working. Tests in
`backend/internal/authz/` pin those formats so drift fails a test.

Run just those packages with:

```sh
CGO_ENABLED=0 go -C backend test ./internal/authz/... ./internal/controlbus/...
```

If you bump the pinned better-auth version, regenerate the fixtures these tests assert
against (see `contract_test.go` and `jwt_test.go` in `backend/internal/authz/`).

## Frontend (`web/`)

Run all three from `web/`:

```sh
pnpm build
pnpm typecheck
pnpm test
```

| Command | What it does |
|---|---|
| `pnpm build` | Vite build into `.output` (the Nitro server bundle). This also runs the TanStack Router code generator, which writes `app/routeTree.gen.ts`. |
| `pnpm typecheck` | `tsc --noEmit`. It reads the generated `app/routeTree.gen.ts`, so the route tree must exist first (see below). |
| `pnpm test` | Vitest. Covers the realtime frame parser (`app/lib/events/frames.test.ts`) and the `cacheBridge` event reducer (`app/lib/events/cacheBridge.test.ts`). |

<Callout type="warn">
On a fresh checkout, run `pnpm build` (or start `pnpm dev`) **before** `pnpm typecheck`.
The typecheck reads the generated `app/routeTree.gen.ts`; without it, the typecheck fails
because the route tree is missing. The build (and the dev server)
both generate that file.
</Callout>

## Marketing and documentation (`site-marketing/`)

Run `pnpm build` and `pnpm typecheck` from `site-marketing/` after changing its
MDX or application code. Build first so the generated route tree is available.
