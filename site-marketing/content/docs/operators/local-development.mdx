title: Local development

The setup that gives the fastest edit loop is: run MySQL and Redis in Docker, and
run the three app processes directly on your machine — the **API** (the public
API), the **gateway** (the WhatsApp engine), and the **frontend**. The
gateway reloads on file change with [`air`](https://github.com/air-verse/air);
the frontend runs the Vite dev server, which hot-reloads in the browser; the
API is small and stateless, so you restart it by hand when you change it.

## Prerequisites

| Tool | Why | Notes |
|---|---|---|
| Go 1.26+ | Build and run the API and gateway | The Go toolchain auto-switches to the version pinned in `go.mod` (`GOTOOLCHAIN=auto`). |
| Node 22+ with pnpm | Build and run the frontend | Run `corepack enable` once to get pnpm. |
| Docker | Run MySQL and Redis | Used for local infrastructure only; the apps run on the host. |
| `air` | Gateway hot reload | Watches Go files and rebuilds `./cmd/gateway` on change. |
| `golangci-lint` | Go linter | Run with `make lint`. |

You do **not** need a C compiler. The gateway's WhatsApp keystore uses a pure-Go
SQLite driver, so everything builds with `CGO_ENABLED=0`.

## Get the source code

Clone the [WhatsApp Gateway source repository](https://github.com/rama-adi/quick-whatsapp-gateway) and enter the checkout directory:

```sh
git clone https://github.com/rama-adi/quick-whatsapp-gateway.git
cd quick-whatsapp-gateway
```

Paths such as `backend/`, `web/`, and `deploy/` are relative to this directory.

## First run

Run these once, from the WhatsApp Gateway checkout directory (the directory containing `Makefile`), to set up config, start infrastructure, and
create the database tables:

```sh
cp deploy/.env.example deploy/.env    # API + gateway env — fill the secrets below
cp web/.env.example web/.env          # frontend env — fill BETTER_AUTH_SECRET
make infra-up                         # start MySQL + Redis (ports bound to localhost)
make migrate                          # create WA app-data tables (runs `backend/cmd/migrate up`)
cd web && pnpm install && pnpm db:migrate && cd ..   # create the auth tables (drizzle-kit)
```

Supply the application secrets before starting. Generate independent 32-byte keys with
`openssl rand -base64 32`; retain them across restarts:

| Variable | File | What to set |
|---|---|---|
| `PKI_ENCRYPTION_KEY` | `deploy/.env` | Encrypts the private control-plane CA key. |
| `OIDC_KEY_ENC_KEY` | `deploy/.env` | Encrypts OAuth signing keys. |
| `OAUTH_CLIENT_SECRET_PEPPER` | `deploy/.env` | Protects OAuth client secrets. |
| `APP_ENCRYPTION_KEY` | `deploy/.env` | A base64-encoded 32-byte AES-GCM key. Generate with `openssl rand -base64 32`. Encrypts webhook secrets at rest. |
| `BETTER_AUTH_SECRET` | `web/.env` | The better-auth signing secret (32+ chars). Generate with `openssl rand -base64 32`. |

`deploy/.env` is one file read by **both** Go processes: the API reads the
`API_*`, database, Redis, PKI, and better-auth verification settings; the gateway
reads its control-plane, engine, journal, and SQLite settings.

Before starting the gateway, provision its identity through the API admin gateway
flow. Configure `GATEWAY_ID`, its one-time enrollment token, the operator root PEM
at `GATEWAY_BOOTSTRAP_CA_FILE`, and persistent credential/journal paths. Use
loopback addresses for both private gRPC listeners when running on the host; the
example container service names do not resolve on the host. See [deployment](/docs/operators/deploying).

There are two separate migration tools, one per set of tables — don't mix them up:

- `make migrate` creates the WhatsApp app-data tables (gateways, sessions,
  contacts, …). API startup also applies these through API-owned golang-migrate.
- `pnpm db:migrate` (run in `web/`) creates the better-auth tables (user,
  session, apikey, organization, …) with drizzle-kit.

## Day to day

After the first run, start the infrastructure once, then run each process in its
own terminal:

```sh
make infra-up    # MySQL + Redis (skip if already running)
make dev         # terminal 1: gateway under air; reloads on change
make api         # terminal 2: the API; restart after API edits
make web         # terminal 3: frontend dev server (pnpm dev) on :3000
```

The API listens on HTTP `:8090` and gRPC `:8081`; the gateway listens on `:8080`
(internal). Open `http://localhost:3000` for the frontend. The browser calls the
**API** at `:8090`, never the gateway directly; the API's CORS config
already allows `http://localhost:3000` (via `FRONTEND_ORIGINS`), so the three work
together with no extra setup.

<Callout type="info">
`make dev` runs `air`, which builds and watches **`./cmd/gateway`** (the gateway)
only. The API is a separate process — `make api` runs it with `go run
./cmd/api`, with no hot reload, so restart that terminal after you change API
code. The gateway still hot-reloads on every save.
</Callout>

Prefer the API in a container? Run the gateway in Docker and add the `api`
profile — then only the frontend runs on the host:

```sh
docker compose -f deploy/docker-compose.dev.yml --profile api --profile gateway-dev up -d --build
make web   # frontend on the host
```

The gateway and API communicate over private mTLS gRPC listeners on the Compose
network. Use `deploy/docker-compose.grpc-control-plane.yml` for the enrollment,
certificate, journal, and private listener configuration. The browser still uses
the API's public HTTP listener on `:8090`.

To wipe the dev database and start clean, run `make infra-reset` (this removes the
Docker volumes), then re-run the two migrate steps from the [first run](#first-run).

## Running the gateway or API in Docker instead

By default you run the Go processes on your host. If you want one to run inside a
container instead — for example to match the production OS and Go toolchain
without installing Go locally — the dev compose file has three profiles. The
frontend always stays on your host under Vite.

| Command | What it does |
|---|---|
| `docker compose -f deploy/docker-compose.dev.yml --profile api --profile gateway up -d --build` | Runs API plus the production gateway image. The gateway waits for API readiness/migrations. |
| `docker compose -f deploy/docker-compose.dev.yml --profile api --profile gateway-dev up -d --build` | Runs API plus the gateway under `air`; the gateway waits for API readiness/migrations. |
| `docker compose -f deploy/docker-compose.dev.yml --profile api up -d --build` | Runs the API from its production image (`deploy/Dockerfile.api`), publishing HTTP `:8090` and gRPC `:8081`. |

Run one gateway profile per identity and persistent keystore. The API owns WA
migrations and connects to the host-side frontend JWKS through
`host.docker.internal`; gateways do neither. The Compose files override network
addresses and persistent paths where container values differ from host values.

## Environment variables

Router and gateway settings live in `deploy/.env` (template:
`deploy/.env.example`); frontend settings live in `web/.env` (template:
`web/.env.example`). Both templates document every variable with its default. The
ones a contributor usually cares about first:

### API and gateway (`deploy/.env`)

| Variable | Read by | Purpose |
|---|---|---|
| `API_HTTP_ADDR` / `API_PUBLIC_GRPC_ADDR` | API | Public REST and gRPC listeners. |
| `API_GATEWAY_GRPC_ADDR` | API | Private control/enrollment listener. |
| `API_GATEWAY_TLS_IDENTITY_DIR` | API | Persistent mTLS identity directory. |
| `PKI_ENCRYPTION_KEY` / `PKI_ENCRYPTION_KEY_ID` | API | CA key custody; preserve across deployments. |
| `MYSQL_DSN` / `REDIS_URL` | API | Shared application persistence and work transport. |
| `BETTER_AUTH_URL` / `BETTER_AUTH_JWKS_URL` | API | Accepted JWT issuer and public signing keys. |
| `FRONTEND_ORIGINS` | API | Allowed browser origins. |
| `GATEWAY_ID` | gateway | Enrolled identity and session owner. |
| `GATEWAY_CONTROL_PLANE_ADDR` | gateway | API private listener to dial. |
| `GATEWAY_ENGINE_GRPC_ADDR` / `GATEWAY_ENGINE_GRPC_ADVERTISE_ADDR` | gateway | Engine listener and address the API can reach. |
| `GATEWAY_CREDENTIAL_DIR` / `GATEWAY_BOOTSTRAP_CA_FILE` | gateway | Persistent certificate and operator trust root. |
| `GATEWAY_ENROLLMENT_TOKEN` | gateway | One-time bootstrap credential; remove after enrollment. |
| `GATEWAY_JOURNAL_PATH` / `WHATSMEOW_STORE_DSN` | gateway | Persistent event/command journal and device keys. |
| `GATEWAY_HTTP_ADDR` | gateway | Internal health, readiness, and metrics only. |

### Frontend (`web/.env`)

| Variable | Default | What it does |
|---|---|---|
| `BETTER_AUTH_SECRET` | — | better-auth signing/encryption secret (32+ chars). Required. |
| `BETTER_AUTH_URL` | `http://localhost:3000` | The frontend's own base URL, used as the JWT issuer and audience. |
| `DATABASE_URL` | `mysql://…@localhost:3306/wa_gateway` | MySQL connection for the frontend's Drizzle client: better-auth tables (read/write) plus read-only WA queries. |
| `GATEWAY_URL` | `http://localhost:8090` | Legacy-named server-side API base URL. |
| `VITE_GATEWAY_URL` | `http://localhost:8090` | Legacy-named browser API base URL. |
| `PUBSUB_REDIS_URL` | `redis://localhost:6379` | Redis the frontend uses to publish revocations consumed by the API. |
| `USER_REGISTRATION_ENABLED` | `true` | Whether people can sign themselves up. Set `false` to lock it down. |

<Callout type="warn">
The SQLite keystore (`WHATSMEOW_STORE_DSN`) holds each connected number's device
keys. If you lose that file, every number has to be paired again. It's a local
file in dev; in production keep it on a persistent named volume and back it up.
</Callout>

## Smoke test

`scripts/smoke.sh` runs the automatable part of the auth flow against a running
stack **through the API**: it registers a user, gets a JWT from better-auth,
calls the API with that token, creates a session, and fetches the session's
pairing QR code. It stops with an error on any unexpected HTTP status. The steps
that need a real phone (pair, send, subscribe) are printed as manual instructions
at the end.

Override `SMOKE_EMAIL`, `SMOKE_PASSWORD`, and `SMOKE_NAME` as needed; the script
JSON-encodes these values, including quotes, backslashes, and Unicode.

```sh
BETTER_AUTH_URL=http://localhost:3000 API_URL=http://localhost:8090 scripts/smoke.sh
```

`API_URL` is the API's HTTP URL (`:8090`) —
since the gateway no longer authenticates callers directly.

## Marketing and documentation app

Install the separate workspace dependencies once, then run its development server
from the WhatsApp Gateway checkout directory (the directory containing `Makefile`):

```sh
cd site-marketing && pnpm install
cd ..
make marketing
```

Open the local URL printed by Vite. The `site-marketing/` application contains the landing page and
operator/developer MDX docs; dashboard user guides remain in `web/content/docs/`.
The marketing app runs independently of MySQL, Redis, the API, and gateways.
After changing its documentation or app code, run `pnpm build` and
`pnpm typecheck` from `site-marketing/`.
